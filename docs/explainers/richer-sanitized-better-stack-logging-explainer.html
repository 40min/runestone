Richer, sanitized Better Stack logging

The sanitizer shipped in 4b08c4a is live but inert — no production code emits a telemetry marker, so no breadcrumb has ever reached a real error event. This plan switches the trail on: five marked log records, one server-generated request ID, and the same default-deny sanitizer as the only export authority.

§ 01

How a log becomes a breadcrumb

fails closed at every gate

A marked log record must survive three default-deny gates before anything reaches Better Stack. Each gate rebuilds the payload from scratch — it never edits the original — and drops everything it doesn't explicitly allow.

Why this design Redact-in-place is fragile: a new SDK field would be exported by default after a dependency upgrade. Rebuilding from an explicit allowlist means a new field simply doesn't survive — the export surface can't grow by accident.

§ 04

The new field: request_id

merge semantics, drawn

A tiny pass-through middleware generates one ID per HTTP request and binds it to Sentry's existing ASGI isolation scope. No inbound IDs are trusted; no response header is exposed. Its value: correlating multiple error events inside one request — a handled 500 plus a late background-task failure, for instance.

Practical notes IDs are not correlated to users or sessions. A DEBUG-level local log of the ID is allowed — the sanitizer owns export, so local logs carry zero risk. WebSocket scopes pass through untouched until a WebSocket-path producer ever exists.
