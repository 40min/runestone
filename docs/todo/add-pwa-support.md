## Outcome

Make the existing Runestone web application installable on supported desktop and mobile browsers, give the installed application correct Runestone identity and icons, and keep the static application shell usable when the network is unavailable.

The first release does **not** make server-backed Runestone features work offline. Authentication, OCR uploads, vocabulary, Recall, grammar retrieval, chat, audio, and all `/api/` traffic remain network-only.

## Complexity assessment

The code change is not fundamentally complicated. Runestone already uses Vite, React, a single application entry point, and an Nginx-served production bundle, so `vite-plugin-pwa` can generate the manifest and service worker with little custom code.

The parts that need care are operational rather than algorithmic:

1. service-worker update behavior must not unexpectedly reload a form, upload, recording, or chat draft;
2. authenticated API responses and user data must never enter a shared runtime cache;
3. Nginx currently gives every `.js` file a one-year immutable cache policy, which would incorrectly include the generated service worker unless an exact override is added;
4. installation and update behavior must be verified on the deployed HTTPS origin, not only in Vite development mode.

Expected effort: roughly one focused engineering day for implementation and automated checks, plus a short deployed-device verification pass. Custom offline workflows, push notifications, background sync, or app-store packaging would be separate, materially larger tasks.

## Current state

- `frontend/package.json` uses React 19 and Vite 7 and has no PWA dependency.
- `frontend/vite.config.ts` enables only the React plugin.
- `frontend/index.html` contains an empty data-URL favicon and no manifest, theme-color, or Apple touch icon metadata.
- `frontend/public/` contains only the default Vite logo.
- `Dockerfile.frontend` builds `frontend/dist` and serves it from Nginx.
- `frontend/nginx.conf` correctly falls back application navigation to `index.html`, but its static-file regular expression applies `Cache-Control: public, immutable` for one year to all `.js` files.
- Production TLS appears to be owned outside this repository by the deployment proxy/Coolify. PWA installation requires the final public origin to use HTTPS; localhost remains sufficient for local checks.
- The existing square `res/runestone_logo.jpeg` is 400x400. It can seed generated icons, but a higher-resolution approved source would produce a sharper 512px icon.

## Proposed decisions

1. **Use `vite-plugin-pwa` with its generated service worker.** Add it as a pinned development dependency and commit both `frontend/package.json` and `frontend/package-lock.json`. Use the `generateSW` strategy with `navigateFallback: 'index.html'` so navigation requests are served the application shell offline; a hand-written service worker is unnecessary for this scope.
2. **Cache only the versioned static app shell.** Precache Vite build output and the PWA identity assets. Configure no API runtime cache and no broad network-response cache. `/api/`, uploads, WebSockets, media generated by the backend, and cross-origin resources remain network-only.
3. **Use a user-controlled update prompt.** Runestone contains forms, image uploads, audio recording, and chat input. Register through `virtual:pwa-register/react` and add a small root-level prompt component, styled like the existing MUI Snackbars, offering `Reload` and `Later` when a new version is ready. The existing Snackbars are component-local state, so this is a new component mounted once at the `App` root, not a reuse of a shared primitive. Do not use automatic page reload.
4. **Treat offline support as shell-only.** A previously loaded build may reopen offline, but data-dependent actions should continue to show their existing network errors. Do not claim that Runestone itself is fully usable offline.
5. **Keep installation browser-native in v1.** Do not add a custom Install button or persist the `beforeinstallprompt` event. Users install through browser/OS UI. A discoverable in-app install affordance can be a follow-up if product evidence justifies it.
6. **Use root scope and standalone display.** Proposed manifest values: `name: Runestone`, a concise `short_name`, `start_url: /`, `scope: /`, `display: standalone`, and colors matching the existing dark application shell.
7. **Use explicit cache headers for PWA control files.** Serve `/sw.js` and `/manifest.webmanifest` with revalidation/no-cache semantics before the generic static-asset location. Registration code is inlined into the bundle through the React virtual module, so no separate `/registerSW.js` is generated. Keep content-hashed Vite assets immutable.

### 1. Add generated PWA metadata and assets

Owner: frontend implementation.

Write set:

- `frontend/package.json`
- `frontend/package-lock.json`
- `frontend/vite.config.ts`
- `frontend/index.html`
- PWA icon files under `frontend/public/`

Work:

- Install the current Vite-7-compatible `vite-plugin-pwa` release as a development dependency and update the lockfile through npm.
- Configure `VitePWA` to generate and inject `manifest.webmanifest`, register a root-scoped service worker, clean outdated caches, precache only build/static assets, and serve `index.html` for navigation requests via `navigateFallback` so the shell reopens offline.
- Add at least 192x192 and 512x512 PNG icons plus an Apple touch icon (square artwork is fine for iOS; it does not need maskable treatment). Add a maskable icon only if the artwork passes the maskable safe-zone check; otherwise generate a separate padded maskable asset.
- Replace the empty favicon and add theme-color/Apple metadata to `index.html` where the plugin does not generate it.
- Keep PWA behavior disabled in ordinary Vite development unless a specific manual test enables it; stale development service workers are a common source of misleading results.
- Do not add `runtimeCaching` rules for `/api/` or authenticated content.

Exit gate: a production build contains a valid manifest, correctly sized icons, registration code, and generated service worker; its precache manifest contains no API URL or user-derived data.

### 2. Add safe update UX

Owner: frontend implementation.

Write set:

- a small PWA registration/update component under `frontend/src/components/`
- its focused test
- `frontend/src/main.tsx`
- `frontend/src/vite-env.d.ts` if the plugin's React virtual-module types require it

Work:

- Register the worker with the React virtual module.
- When `needRefresh` is raised, show a Runestone-styled prompt with explicit `Reload` and `Later` actions.
- Call the plugin update callback only after the user chooses `Reload`.
- Keep registration failure non-fatal: log a concise technical error and leave the web application usable.
- Test prompt visibility and both actions with the virtual registration module mocked. Do not try to emulate the browser service-worker lifecycle in jsdom.

Exit gate: an update cannot silently discard in-progress user input, and unsupported/failing service-worker environments still render the normal application.

### 3. Fix production cache headers

Owner: frontend/deployment implementation.

Write set:

- `frontend/nginx.conf`

Work:

- Add an exact-match location for the generated service-worker file ahead of the generic `.js` rule.
- Use `Cache-Control: no-cache` (or an equivalently revalidating policy) for the service worker, `manifest.webmanifest`, and `index.html`.
- Preserve the one-year immutable policy for content-hashed assets.
- Ensure `manifest.webmanifest` is served with a valid manifest/JSON content type by the production Nginx image.
- Preserve the existing `/api/` proxy, SPA fallback, microphone permission, and WebSocket behavior. The CSP needs no change: `script-src 'self'` already permits fetching the same-origin service worker.

Exit gate: `curl -I` against the built container shows revalidation for PWA control files and immutable caching only for hashed assets.

## Non-goals and follow-ups

- Offline authentication or offline storage/synchronization of vocabulary, Recall, grammar, chat, images, audio, or OCR results.
- Background sync, push notifications, periodic sync, share targets, file handlers, shortcuts, or badging.
- App Store, Microsoft Store, or Play Store packaging and submission.
- A custom install button or onboarding campaign.
- Native-device capabilities beyond those already used by the web application.
- Backend, database, or API contract changes.

Each non-goal requires separate product acceptance, especially any feature that stores authenticated or user-generated data in browser caches.

## Rollback

- Revert the PWA registration/configuration and redeploy.
- If a broken worker has already reached clients, deploy a one-time unregistering/cleanup worker at the same URL and scope before removing the endpoint; simply deleting `sw.js` may leave existing registrations controlling clients.
- Keep the exact service-worker cache-header override until the cleanup release has reached installed clients.
- Publish the client recovery path: close installed windows, clear Runestone site data/unregister the service worker, then reopen the normal HTTPS site.
